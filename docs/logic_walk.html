The design in one place w2

The rules (Vatsal, 8 Oct 2026):

1. A change is drafted in one rule set. The draft goes: open, checked, impact preview done, in approval, approved (or sent back, then open again), published. Or it is discarded. Approval covers the changes, the rollout and the reason clients read. Changing any of them after approval sends it back.

2. Publishing is not applying. A release reaches every plan built or refreshed from its effective date. A plan that already exists stays on its versions until its next refresh. The main board today differs: L06 recalculates every affected client when a change is published, and Q01 runs on each publish. These wireframes draw this way beside it and change nothing on the board. I04 HoA Core Platform is described as holding a client's numbers steady between their reviews (7 Oct 2026 call; LQ17, LQ18). In M2's registry, a changed assumption marks the affected plans for recalculation.

3. Only the latest live release of each rule set is used; older ones are records. A plan refresh reads every rule set's live version when it starts, and never combines two versions of one. Risk profiling is the exception: it is read as of the client's last questionnaire, and the snapshot names that version.

4. A release is pushed now to existing plans only if its rollout says so. The test, printed on L06: would a prudent adviser phone this client about it today?

5. A plan more than 120 days old refreshes at the next app open (the max plan age). A lapsed or cancelled account's plan freezes, and refreshes when the client returns.

6. A release is never effective before it is published. While it waits for its effective date, its rule set takes no other change, except an urgent hold.

7. Every plan refresh writes a plan snapshot. It holds the inputs, the rule set and plan engine versions, each goal's cell, the outputs and the actions. It also holds what changed, with a reason on every line (house view, your numbers, your confirmation, time passing, staff edit), the update type, and what the client did. Releases and snapshots are only added, never edited; a correction is a new record. The record is the stored output, not a promise to recalculate it. On the main board today, L08 reads "the register can reproduce any advice given".

8. The update type decides what the client sees (the update types table). Targets are always recalculated. Instalments change as a set or not at all. If any sub-asset class's amount moves past the tolerance band, all are updated to their targets; if none does, nothing changes. A fund on hold or exit updates its own sub-asset class. An update still waiting at the next refresh is replaced; the new one shows what changed against the current plan. On the main board, H05 merges waiting updates into one.

9. A fund leaving the approved list goes on hold by default (no new money, units kept). Exit (sell out) is a separate decision, with its own reason. A hold that would empty a sub-asset class is blocked until the same draft adds a fund to it. The app never stops a running SIP on its own. It runs until the client accepts the update, and the update says so in plain words.

10. New score ranges reach a client only when they next complete or reconfirm the questionnaire.

11. Market inputs reach new plans and new investing actions only. Every threshold has a buffer on either side.

12. Undo is three actions, not a mirror roll-back. Pause: the release stops being the latest, and refreshes use the one before it. Withdraw: every update built on it and not yet accepted is replaced by a refresh on the release before it. Clients' own changes are kept, and plan history reads "an update was withdrawn". Correction: a new release. Every current plan built on the paused release is refreshed on it at once: first plans, accepted updates, no-action and information updates alike. A client sees an update only if something moves for them.

13. Maker-checker on every change: the maker cannot be the checker, and only the Principal officer publishes. One exception: the urgent hold. The Principal officer places it alone, folding draft steps 1 to 8 into one action. It may carry only the fund weights it needs to pass the limits (L09). Compliance is told at once. A second person ratifies it within two working days; until then it stays in force and shows as overdue on L08, L10 and L11 (LQ30).

14. Compliance signs an Assumptions or a Risk profiling change before it is published. An Assumptions change alters the assumption lines and the reveal (R08, R09, G01's copy). A Risk profiling change alters the risk profile a client is told (D09). Compliance is told of every other change when it is published, and of an urgent hold at once. Most plan screens carry a compliance flag on the main board, so a wider rule would hold up every change (LQ45).

15. Staff use one sign-in for the admin screens and the logic panel: the one decided for M03 on 7 Oct 2026. Roles are fixed; staff cannot make new ones. A greyed-out button is never the real check: the server checks every change. 2FA is asked again to publish (7 Oct 2026 call), schedule, pause, withdraw, place an urgent hold, ratify one, change a role and export.

16. Allocation is data: axes, the allocation matrix, model portfolios. Funds attach to sub-asset classes, not to cells. A new horizon bucket, or a new axis on a field the app already holds, is data. An axis that needs a new question needs a new app version.

17. A due review that changes nothing is still recorded: "reviewed, no change", signed by the Principal officer.

18. A draft starts from its rule set's live version. If that version moves while the draft is open (an urgent hold), the draft moves onto it. Its checks and impact preview then run again before approval.

19. A client screen never recalculates a plan number when it opens. It shows the current plan; H05 shows the waiting update. Between refreshes only net worth today moves, with holdings and prices (Gaurav, 7 Oct 2026 call).

20. A house-view release reaches a client on a calendar they were told about: assumptions yearly, effective 1 April; the approved fund list quarterly. It comes inside their own review, with its reason. A release that fails the push test gets no notification; the client email explains it (7 Oct 2026 call).

21. Sample plans (R12) and the assumption lines (R08, G01) are remade on a release's effective date, and dated. A saved reveal (X01) records what was shown. It stays, and the nudges keep quoting it, until the person sketches again.

A release goes: scheduled, effective, replaced (a later one of its rule set is effective; plans may still be on it), closed (no active plan is on it). Or it is paused, then corrected. Each step is in the audit trail: who, when, why. At every stage an Adviser or Support can read on L15 which versions a client is on, and why their last update said what it said.

The update type is always decided per client. The rollout table lists the types each kind of change can produce. A push refreshes every plan it picks, but messages a client only for action required or urgent action.

A hold resets the remaining fund weights to 100 for new money (largest remainder, whole numbers). It then checks the limits (L09) before it is placed. If a limit breaks, the hold screen says so and asks for fund weights.

Each pushed release has rollout batches (LQ14). An urgent hold or a correction goes to everyone at once. A routine hold goes to 200 clients an hour, 10:00 to 18:00 IST. An exit goes in even daily batches over five working days.

Tolerance band: per sub-asset class, the larger of Rs 1,000 or 10 percent of the running amount; for a goal's funded share, 5 points. Amounts are whole hundreds, and a sub-asset class's funds add up to its amount (largest remainder). For a client not investing through the app, each new target is compared with the last target shown.

Second reasons: a fund entering or leaving a client's fund weights also names the Funds release behind it. A risk profile changed at a questionnaire reads your confirmation; it also names the Risk profiling release if the same score read differently before.

Why four update types: under the M4 reconciliation rule, most plans invest the whole surplus. So a change in returns or inflation leaves instalments as they are, and moves how far they are expected to go. In a rough run of an assumptions change, per 100 plans: about 33 no action, 54 information, 13 action required. Information asks for nothing, so it is not chased.

The client email (7 Oct 2026 call): one per house-view release that alters what clients see. It says what changed, why, and that the plan takes it up at the client's next review, with the date. Its wording is to come, kept with the other message wording. When it goes out: LQ33.
