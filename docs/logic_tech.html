At every stage, an Adviser or Support can open L15: the versions a client is on, and why their last update said what it said.

A sent change's status: set for a date, live, replaced (a later change to its rule set is live; plans may still be on it), closed (no active plan is on it); or paused, then fixed. Every status change is logged: who, when, why.

1. Versions. A rule set's versions never change. A sent change makes one live from its go-live time. The live version at any moment: the latest sent change live by then, neither paused nor superseded.

2. What holds a plan. A plan is the client's current saved copy, carrying the five rule set versions and the plan engine version; nothing else holds it. Risk scores are stamped as of the last questionnaire, so a plan can read rs-1 after rs-2 is live (L15 shows both). The board stamps two today (G01: assumptions_version, instrument_set_version); the other three are added.

3. Reading. Plan screens read the current saved copy, H05 the waiting update; none calls the plan engine on opening. The one exception: net worth today, from holdings and prices as last updated.

4. Refresh. The inputs on file, the as-of time and the live versions go to the plan engine. The result is stored as a saved copy, compared with the current one, given a size and shown.

5. What starts a refresh: a review done (Q01, Q05), a life event (Q06), a sharpen, the annual confirmation (Q04), a questionnaire retake, a staff edit or forced re-run (M03), a push, an app open past the 120-day limit, a pull-back, a fix.

6. At the next refresh: nothing runs when the change is sent; the surfaces job runs at go-live.

7. Pushed now. The change picks plans with a running SIP into the fund, a pending step naming it, a verified holding of it, or a current saved copy made on a named sent change. The rollout job refreshes them in batches. It is idempotent per client and change, can pause and resume, and retries a failed client.

8. Set for a date: live by its go-live time alone, since point 1 compares times. No midnight job has to succeed for new plans to be right.

9. The 120-day limit, checked at app open: a latest saved copy over 120 days behind a live Assumptions, Client groups or Funds change is refreshed on the inputs on file.

10. Pause, pull back, fix. Point 1 skips a paused change. Pull back refreshes, on the change before, every plan with an unaccepted update made on the paused change, and marks the old saved copy withdrawn. A fix is a new sent change; its rollout picks every plan whose current saved copy was made on the paused change.

11. Timing. A running refresh keeps the versions it read at its start. A client holding an update when it is pulled back sees the notice on the next screen. A draft moves onto the new version when its rule set's live version moves.

12. Blocks. An overdue annual confirmation blocks a refresh (Q04 on the board); a lapsed account is frozen. LQ43: whether a pushed update gets past an overdue confirmation.

Finding a goal's group: read its range in each grouping from the client's inputs; take the group table rows matching every grouping (a range or "any"); the row naming the most ranges wins. The no-gap check proves on the draft that exactly one row always wins.

The no-gap check walks every combination of ranges, the product of the range counts: 3 x 3 = 9 at launch, 3 x 4 = 12 after REL07, 3 x 4 x 2 = 24 in the discarded draft. Twenty groups (guessed on the 7 Oct 2026 call) means two groupings cut finer, or three groupings.

"Any" rows keep the group table shorter than the group count: 7 rows for 9 groups, 10 for 12.

Mixes are fewer than groups, and fund baskets fewer than mixes, so a fund change is one edit however many groups exist.

A small group has few goals; the trial run marks it. A cut the client base cannot fill is a draft to discard (L03b).

A group's history comes from the Client groups versions: the row covering it, and that row's mix, in each sent change. No version is stored per group.

Needs an app update: a grouping on a field the app does not yet ask for. LQ5: a ceiling on groupings and ranges.

The plan JSON contract (W03) carries each goal's group and mix (cohort, portfolio) in every saved copy.

What the app does at run time t7

From the moment a hold or an exit is sent, no new order is made for that fund (E03 and E11 as drawn). If orders leave the app through a link, the link's fund list leaves it out (LQ36).

The app never stops a running instalment on its own.

A refresh never mixes two versions of one rule set.

Plan screens print "Assumptions as of <date>" from the saved copy; the saved first result and its nudges read the stored first result.

Launch or later turns on one question: can it be added afterwards without losing anything? A version never stamped on a plan cannot be recovered; a chart over stored rows can be drawn any day.

Failure cases, and what the system does:

A refresh fails in a rollout: the job retries that client; L11 lists each failure by client.

A refresh during a pause: one starting after it uses the change before; one already running keeps the versions it read at its start.

gap, to be decided: whether a pull-back or a fix waits for refreshes still running

An update pulled back while open: the notice shows on the next screen; a refresh on the change before replaces it, keeping the client's own changes; plan history reads "an update was withdrawn".

Three sent changes picked up at once: one refresh reads every live version at its start and writes one saved copy (risk scores: as of the last questionnaire). What changed is drawn against the current saved copy, a reason on every line; a house-view reason names its sent change. An update still waiting is superseded.

A refresh past the 120-day limit fails: the app opens on the old plan and tries again at the next open.

A blocked refresh (How a change reaches a plan, point 12): a lapsed account refreshes on return; the block is stored as an interaction (rebuild_blocked) and listed on L08 and L15.

A revoked session ends at once: the next request is refused and logged.

A draft whose rule set moves (an urgent hold, say): it moves onto the new version, and its checks and trial run rerun before the second check.

A first plan made between sending and go-live: it uses the live versions, then takes the change like any existing plan. LQ21: whether it should use the new values.
